## 1. 前提: 元の Seg2Any（FLUX.3 版）は 1 回の forward で何をしているか

### 1.1 トークン列
transformer には 3 種類のトークンを並べて入れる。

```
[ txt (global caption + regional caption) | img (ノイズの乗った画像) | cond (輪郭画像) ]
   約 400〜800 トークン                      1024 トークン              約 330〜440 トークン
```

- **txt**: Qwen3-VL で埋め込んだ文章。global caption と、領域ごとの regional caption をつないだもの
- **img**: 生成中の画像の潜在。512² なら 32×32 = 1024 トークン。最終的に出力するのはここだけ
- **cond**: 領域の輪郭（白線）を VAE で潜在にしたもの。線のないトークンは捨てる（`is_filter_cond_token`）

**img は全体の 5〜6 割しかない**。残りは txt と cond。この点が ③ の効き目の源になる。

### 1.2 ブロックの構造（FLUX.3 klein）
```
mode blocks ×5   : txt / img / cond がそれぞれ自分の中だけで self-attention（重みもストリームごとに別）
single blocks ×28: [txt, img, cond] を 1 本につないで attention（重みは共有、modulation はストリームごと）
```

### 1.3 Seg2Any の attention マスク（single blocks）
誰が誰を見てよいか（行 = 見る側、列 = 見られる側）。

```
            見られる側 →   txt      img      cond
見る側  txt              ○(*)     ○(*)      ×
        img              ○(*)     ○        ○
        cond             ×        ○        ○
(*) regional caption は自分の領域の img とだけ、などの領域制限つき（Seg2Any の SAA / AIA）
```

ポイント: **元の Seg2Any では、cond はもともと txt を見ない**。cond が見るのは img と自分だけ。

### 1.4 LoRA
Seg2Any は OminiControl にならって LoRA を 2 つ持つ。
- `default`: txt と img を通すときに使う（rank 16）
- `cond`: cond トークンを通すときだけ使う

single blocks では、同じ線形層に txt+img は `default`、cond は `cond` を当てて別々に計算し、attention だけ 1 本で取る。
LoRA は重みに融合されておらず、毎回 `W x + B(A x)·s` を計算している。さらに peft の仕組み上、選んでいない側の LoRA も scaling を 0 にして計算している。

### 1.5 timestep の扱い
- img の modulation は、今の timestep と飛び先の timestep（蒸留版は flow map なので「どこまで飛ぶか」も入力になる）から作る
- txt と cond は、元の Seg2Any でも timestep = 0 扱い。ただし蒸留版では **飛び先の timestep は txt / cond にも足されている**ので、txt / cond の modulation はステップごとに変わる

### 1.6 時間の内訳（A6000、1 回の forward 365 ms）
| | ms |
|---|---|
| 素の計算 | 189 |
| LoRA 未融合のコスト | +86 |
| 領域マスク付き attention のコスト | +49 |
| cond トークンのコスト | +74 |

1 枚の生成時間の 96% が transformer。ステップごとに同じ計算をしている部分が大きい。

## 2. ① LoRA 融合（default LoRA を重みに足し込む）

### 2.1 何をしているか
線形層の計算は `y = W x + s·B(A x)`（W: 元の重み、A, B: LoRA、s: scaling）。これは
`y = (W + s·BA) x`
と同じなので、`W' = W + s·BA` を一度だけ作って重みを置き換えれば、毎回の LoRA 計算がいらなくなる。

難しいのは、**同じ線形層を txt+img（default）と cond（cond LoRA）が共有している**こと。W に default を足し込むと、cond を通すときにも default が乗ってしまう。そこで:

- txt / img を通すとき: peft を無効にして W' だけで計算（LoRA の計算はゼロ回）
- cond を通すとき: `W' x − s_d·B_d(A_d x) + s_c·B_c(A_c x)`。default の分を LoRA で差し引き、cond の分を足す

cond は 400 トークン前後しかないので、差し引きのコストは小さい。実装は `fuse_default_lora` と `fused_select_lora`。232 個の線形層を融合している。

### 2.2 元の Seg2Any から何が変わったか
- 計算式としては何も変わっていない（足し算の順番を変えただけ）
- 違いは bf16 の丸めだけ。1 回の出力で相対誤差 1〜5×10⁻²、画像で PSNR 37 dB。見た目は区別できない
- 学習はしていない。今の LoRA のまま使える

### 2.3 結果
- 4 ステップで 1.22 s → 0.98 s（1 回の forward 234 ms → 177 ms）
- val55 で mIoU・bIoU・KID・CLIP のどれも今のままと区別できない（mIoU の対応のある検定 p = 0.44）

### 2.4 なぜうまくいくか
数式上まったく同じ計算なので、品質が変わらないのは当然。速くなるのは、毎回やっていた「LoRA の 2 つの小さな行列積 × 2 アダプタ分」と「peft の分岐」が消えるから。

## 3. ③ txt / cond の一方向化 + K/V キャッシュ

### 3.1 アイデア
ステップをまたいで毎回同じ計算をしているのに、毎回やり直している部分がある。txt と cond は、入力（文章・輪郭）自体はステップごとに変わらない。それでも毎ステップ計算し直しているのは、次の 2 つのせいで、隠れ状態がステップごとに変わるから。

1. **single blocks で txt と cond が img を見ている**（img は毎ステップ変わる）
2. **txt と cond の modulation に飛び先の timestep が入っている**（ステップごとに変わる）

そこで、この 2 つを止める。

1. single blocks のマスクで、**txt の行 → img の列** と **cond の行 → img の列** を塞ぐ（一方向化）
2. txt / cond の modulation を、timestep = 0・飛び先 = 0 の**定数に固定**する

すると txt と cond の隠れ状態は文章と輪郭だけで決まり、どのステップでも同じになる。
1 ステップ目に各 single block の txt / cond の Key と Value を保存し、**2 ステップ目以降は img トークンだけを計算**する。

### 3.2 マスクはこう変わる

```
            txt   img   cond                    txt   img   cond
txt         ○     ○     ×          →     txt    ○     ×     ×
img         ○     ○     ○                img    ○     ○     ○      ← img は今まで通り全部見られる
cond        ×     ○     ○                cond   ×     ×     ○
              元の Seg2Any                          ③
```

img の行は変えていない。**画像は今まで通り、文章と輪郭の情報をすべて読みにいける**。
失われるのは逆向き、つまり「文章と輪郭が、今の画像を見て自分を更新する」流れだけ。

### 3.3 2 ステップ目以降の計算
```
1 ステップ目: [txt | img | cond] を全部計算し、28 個の single block それぞれで txt と cond の K, V を保存
2 ステップ目〜: img だけ計算する
   - mode blocks: img のストリームだけ
   - single blocks: Query は img の 1024 トークンだけ。Key / Value は [保存した txt | 今の img | 保存した cond]
```

列の並び（txt, img, cond）は元のマスクと同じにしてあるので、img の行のマスクは元のものをそのまま切り出して使える。

### 3.4 キャッシュが「近似」ではなく「厳密」である理由
一方向化と modulation の固定をすると、txt / cond の隠れ状態は**数学的に**ステップに依存しなくなる。なので、使い回しても計算結果は変わらない。
検算（`check_cache.py`）でも、毎ステップ全部計算した場合と使い回した場合の出力は、LoRA 融合後は**ビット単位で一致**した。
つまり ③ の品質は「一方向化 + modulation 固定をしたモデルの品質」そのもので、キャッシュによる劣化はない。

### 3.5 速度
2 ステップ目以降の forward は、トークン数で見て約 1900 → 1024（約 54%）になる。さらに cond 用の LoRA も 1 回しか走らない。

| | 1 回目 | 2 回目以降 | 1 枚 |
|---|---|---|---|
| 今のまま | 247 ms | 234 ms | 1.22 s |
| ① | 184 ms | 177 ms | 0.98 s |
| ① + ③ | 196 ms | **76 ms** | **0.65〜0.69 s** |

効き目はステップ数に比例して大きくなる。16 ステップなら、見積もりで ① だけ約 2.8 s に対して ① + ③ は約 1.3 s。

### 3.6 学習なしでは崩れた
今の重みのまま一方向化すると、
- 器が大きく寄る、具が増えてごちゃつく、配置がマスクからずれる、器が 2 つになる例もある
- val55 で mIoU 0.893 → 0.437、bIoU 0.286 → 0.064、KID 16.9 → 34.0

モデルは「txt と cond も画像を見て更新される」前提で学習されているので、その流れを切ると、後段のブロックに届く txt / cond の表現が想定とずれる。

参考までに、cond だけを一方向化した ②（OminiControl2 と同じ）も試した。具の量は保たれたが、器の輪郭と形が崩れた。「cond が今の画像を見て輪郭を合わせ直す」流れが、学習なしでは輪郭の効きに必要だったと考えられる。

## 4. 自己蒸留で ③ を直す

### 4.1 やり方
- **教師**: 今のモデル（蒸留版 + ラーメン LoRA、全結合 attention）。正解画像の代わりに、教師の出力を「正解」にする
- **生徒**: 教師と同じ LoRA から始めて、③ の計算（一方向マスク + modulation 固定）で動かす
- **データ**: train 500 枚 × seed 4 通り × 4 ステップ = 8000 点。各点で、教師が実際にたどった途中の状態 x_t と、そこでの教師の出力を、デモと同じ推論設定のまま保存した（`precompute_teacher.py`）
- **損失**: 同じ x_t を生徒に入れたときの出力と、教師の出力の二乗誤差
- **学習するもの**: default と cond の両方の LoRA（6750 万パラメータ）。lr 5×10⁻⁵、2000 step、6 GPU、67 分
- 生徒の学習時の計算は `CachedForward(use_cache=False)` で、推論時のキャッシュあり計算と**完全に同じ**（3.4 の検算）

loss は 0.20 → 0.016 まで下がった。

### 4.2 結果（val55）
| | mIoU | bIoU 3px | bIoU 8px | KID×1000 | FID | CLIP-I | 1 枚 |
|---|---|---|---|---|---|---|---|
| 今のまま | 0.893 | 0.286 | 0.551 | 16.9 | 87.1 | 89.40 | 1.22 s |
| ① | 0.894 | 0.286 | 0.551 | 16.8 | 86.6 | 89.36 | 0.98 s |
| ① + ③ 学習なし | 0.437 | 0.064 | 0.109 | 34.0 | 108.8 | 85.14 | 0.69 s |
| **① + ③ 自己蒸留** | **0.890** | 0.270 | 0.537 | **15.7** | **85.3** | 89.31 | **0.65 s** |

- mIoU は今のままと有意差なし（-0.003、Wilcoxon p = 0.20）
- 境界の細部（bIoU）だけ、わずかに低い（-0.016）
- KID / FID はむしろ良い（55 枚なので参考値）
- 見た目も ① とほぼ同じ絵になり、具の過剰や器の二重化は消えた

## 5. 元の Seg2Any から何が変わったか（まとめ）

| 項目 | 元の Seg2Any (FLUX.3 版) | ① | ① + ③ 自己蒸留 |
|---|---|---|---|
| トークン列・入力 | [txt, img, cond] | 同じ | 同じ |
| mode blocks | ストリームごと | 同じ | 同じ |
| single blocks のマスク: img の行 | 領域マスク | 同じ | 同じ |
| single blocks のマスク: txt / cond の行 → img | 見る | 同じ | **見ない** |
| txt / cond の modulation | t = 0、飛び先はステップごと | 同じ | **t = 0、飛び先も 0（定数）** |
| default LoRA | 毎回計算 | **重みに融合** | **重みに融合** |
| cond LoRA | 毎ステップ計算 | 毎ステップ（default を差し引いて） | **1 ステップ目だけ** |
| 2 ステップ目以降に計算するトークン | txt + img + cond | 同じ | **img だけ** |
| LoRA の重み | ラーメン LoRA ckpt-3000 | 同じ | **自己蒸留で更新した LoRA** |
| 再学習 | — | なし | 約 1 時間（正解画像不要） |

変えていないもの: 領域アテンションマスク（SAA / AIA）、cond トークンの作り方と間引き、regional caption、VAE、テキストエンコーダ、ステップ数とスケジュール。

## 6. OminiControl2（CVPR 2026）から何を参考にしたか

OminiControl2 は、OminiControl（FLUX.1 に条件画像を入れる手法。Seg2Any の cond 分岐の元）を速くした論文。主な工夫は「条件トークンの特徴を 1 回だけ計算して使い回す」こと。論文本文に書いていない細部は、公式コード（`Yuanshi9815/OminiControl` の `trainer.py`・`flux_omini.py`）で確認した。

### 6.1 そのまま借りた考え方
1. **非対称な（一方向の）マスクで、使い回しを厳密にする**
   OminiControl2 は、条件トークンが画像トークンを見ないマスクにして、条件の特徴をステップに依存させないようにしている。③ はこれをそのまま txt にも広げた。
2. **マスクなしで KV を使い回すとダメ。マスクを入れて学習し直す**
   論文では、素朴な KV キャッシュは FID が大きく悪化する（Deblur 20.8 → 45.0 など）。マスクを入れて LoRA を学習すれば戻る。③ が学習なしで崩れたのも同じ現象で、「学習すれば戻るはず」と判断できた根拠になった。
3. **条件側の timestep は 0 に固定**
   コードでは条件ブランチに常に t = 0 を入れている。③ では、蒸留版特有の「飛び先の timestep」まで 0 に固定し、学習時から同じ設定にした。
4. **ブランチごとに別の LoRA**
   条件ブランチだけ専用の LoRA を持つ設計。Seg2Any も同じ（`cond` adapter）なので、「cond 用 LoRA は 1 ステップ目しか走らない → 画像側の LoRA だけ融合すればよい」という ① + ③ の組み合わせにつながった。
5. **1 ステップ目に書いて、以降は読む実装の形**
   コードの `cache_mode = "write" / "read"` の作り。`CachedForward` も同じ形にした。

### 6.2 OminiControl2 と違うところ（ここが新規性）
| | OminiControl2 | ③ |
|---|---|---|
| 使い回す対象 | 条件トークンだけ | **条件（cond）とテキストの両方** |
| テキスト | 毎ステップ計算し直す | 1 回だけ |
| 2 ステップ目以降に計算するもの | 画像 + テキスト | 画像だけ |
| 品質の取り戻し方 | マスク付きで一から LoRA 学習（25k iter / タスク）。それでも FID は悪化 | 既存の LoRA から**自己蒸留**（2000 step、正解画像不要）。mIoU は有意差なし |
| 対象モデル・ステップ数 | FLUX.1 dev、主に 28 ステップ | FLUX.3 蒸留版（flow map）、4 ステップ |
| 評価 | FID のみ | mIoU、bIoU、KID / FID、CLIP、対応のある検定 |

Seg2Any ではテキストが長い（regional caption があるので平均 400〜500 トークン、cond と同程度）。なので、テキストまで使い回さないと 4 ステップでは効き目が小さい。実際、cond だけの ② は ① + ② で 0.80 s、テキストも含めた ③ は 0.65 s だった。

### 6.3 借りなかったもの
- **条件画像の縮小（トークン数 1/4）**: Seg2Any では `cond_scale_factor 2` が同じことに当たり、以前の実験で悪化していた。また、③ では cond は 1 回しか計算しないので、縮小してもほとんど得がない
- **線のない条件トークンを捨てる処理**: Seg2Any にもともと入っている（`is_filter_cond_token`）

## 7. なぜうまくいったのか（考察）

確かめたことと、推測を分けて書く。

### 7.1 確かめたこと
- **キャッシュによる誤差はゼロ**: 使い回しあり / なしは、融合後にビット単位で一致した。学習時の生徒の計算と推論時の計算も同じ。「学習ではうまくいくのに推論でずれる」余地がない
- **学習なしの崩れは「一方向化 + modulation 固定」そのものが原因**: 自前実装と、元の forward のマスクを書き換えた版が完全一致したので、実装のバグではない
- **残る劣化は境界の細部**: mIoU（領域が合っているか）は同等、bIoU（境界付近だけで測る）が少し低い。学習の最後でも、最後のステップ（k = 3）の loss が一番大きかった（0.028。他は 0.007〜0.016）。最後のステップは細部を仕上げる段階なので、bIoU の差と符合する

### 7.2 推測（筋の良い説明だが、直接は検証していない）
1. **大事な情報の流れは残っている**
   条件付けで本当に必要なのは「画像が文章と輪郭を読む」向き（img → txt、img → cond）で、③ ではこれを一切切っていない。切ったのは「文章と輪郭が画像を見て自分を作り直す」向きだけ。PixArt や SANA など cross-attention 型の DiT では、テキストはもともと画像から更新されないが、高品質な画像を作れている。テキストを静的にした構造でも十分に生成できることは、既存モデルで示されている
2. **FLUX.3 は前半がもともと「一方向」**
   最初の 5 層の mode blocks は、もともと txt / cond が画像を見ない。変わったのは後半の single blocks だけで、元のモデルからの距離が小さい
3. **変更が「小さな調整」で済む**
   生徒は教師と同じ重みから始まる。直すのは、各 single block で txt / cond が出す K / V の作り方を「画像を見ずに、画像が読みやすい形にする」方向に寄せることだけ。LoRA（rank 16、6750 万パラメータ）で足りる規模だったと考えられる
4. **教師の出力を正解にするので、信号が濃くて安定している**
   普通の拡散学習は「ノイズと正解画像」から学ぶので、損失のばらつきが大きい。自己蒸留では、同じ入力に対する教師の出力そのものを合わせにいくので、1 点ごとの情報量が多く、ばらつきも小さい。しかも蒸留版の 4 ステップでは、通る timestep が 4 種類に限られる。8000 点で入力の範囲を十分に覆えた
5. **KID / FID が少し良くなった理由**
   55 枚では差がばらつきの範囲かもしれない（KID は参考値）。仮説として、生徒は教師の出力の平均的なところに寄るので、まれな破綻（教師が時々出す変な絵）が減った可能性がある

### 7.3 まだ弱い点・次の改善
- **off-policy であること**: 生徒は「教師がたどった状態」でしか学習していない。推論では自分の出力で次の状態に進むので、小さなずれが積み重なりうる（exposure bias）。生徒自身の軌跡の状態で教師に正解を出させる on-policy 学習で、境界の細部（bIoU）がさらに戻る可能性がある
- **評価は val55 だけ、ラーメンだけ**: UECFoodPix など他のデータ、他のステップ数（8、16）での確認はまだ
- **教師が上限**: 生徒は教師（今のモデル）を超えることを狙っていないので、品質の天井は今のモデル
